## 代码要求

- 注释
    - 【必须】为所有对外暴露（pub）的 API（函数/类型/trait 等）补全 rustdoc：一句英文摘要 + 按需提供 # Arguments / # Returns / # Errors / # Examples。
    - 【应当】对“非直观/易踩坑”的内部逻辑写注释，说明意图与关键约束。
-  风格与结构
    - 【应当】遵循统一风格（命名/缩进/错误处理）；避免重复代码、过度工程和高耦合；优先通过模块化/封装提升可维护性。
- 并发
    - 【应当】在能简化正确性/降低锁竞争时，优先消息传递（如 MPSC）而非共享可变状态加锁。
- Idiomatic / Modern Rust
    - 【应当】使用惯用 Rust：?、所有权/借用、清晰的错误类型与边界；在合适场景使用 async、impl Trait 等提升表达力。
- 性能（性能敏感路径）
    - 【应当】尽量减少拷贝，复用 buffer 或采用零拷贝策略。
    - 【应当】优先静态分发，避免不必要的运行期多态，便于内联与优化。

## Implement / Refactor 任务要求

【Implement】是指编写代码，实施功能。【Refactor】指重构代码。

- 在开始编写 / 重构代码之前：
    - 如果我给出了 high-level 的需求和方案，【必须】【Propose】具体的代码实现方案。
    - 如果我给出了非常具体的实现细节，【必须】先归纳成 high-level 的需求和方案，再【Propose】备选的实现方案，并与我的方案进行对比。
    - 【应当】一次性的提出所有实现相关的问题，然后询问我的修改意见。非特殊情况，敲定方案后【不应】向我征求更多的意见。
- 在编写 / 重构代码时：
    - 【必须】按照【代码要求】编写代码。
    - 【应当】进行渐进式开发，【不应】一次性生成和改动大量代码。若大改动无法避免，【必须】【Propose】一个分步骤实现的计划，每一个步骤【必须】视为一个【Implement】 / 【Refactor】任务。
    - 如果单个模块的逻辑超过 600 行代码，【应当】考虑拆分该模块。
    - 【必须】同步更新文档。
